Звіт
з виконання лабораторної роботи
Тема: Розробка програмного брандмауера
Мета роботи
Отримати навички створення власного програмного брандмауера, який здійснює фільтрацію вхідного та вихідного мережевого трафіку за гнучкими правилами, веде базовий журнал подій та забезпечує можливість динамічного оновлення налаштувань без завершення роботи основної служби.
1. Архітектура сервісу та структура правил фільтрації
Програмний брандмауер реалізовано як фоновий сервіс (або консольний застосунок із багатопотоковою архітектурою), що перехоплює мережеві пакети та звіряє їхні параметри з активною таблицею правил.
Структура правила фільтрації
Правила зберігаються у внутрішній структурі даних (або JSON-файлі), що дозволяє їхню динамічну модифікацію. Кожне правило містить такі поля:
•	id: Унікальний ідентифікатор правила (рядок або число).
•	action: Дія при збігу (ALLOW — дозволити, DENY — заблокувати).
•	direction: Напрямок трафіку (INBOUND — вхідний, OUTBOUND — вихідний, ANY — обидва).
•	protocol: Мережевий протокол (TCP, UDP, ICMP, ANY).
•	src_ip: IP-адреса або підмережа джерела (у форматі CIDR, наприклад, 192.168.1.0/24 або ANY).
•	dst_ip: IP-адреса або підмережа призначення (ANY або конкретна адреса).
•	src_port: Порт джерела або діапазон (наприклад, 80, 1024-65535, ANY).
•	dst_port: Порт призначення або діапазон.
•	priority: Пріоритет виконання (ціле число; правила з вищим пріоритетом перевіряються першими).
•	status: Статус правила (ACTIVE — активне, DISABLED — вимкнене).
Інтерфейс керування
Для керування правилами без перезапуску сервісу передбачено два інтерфейси:
1.	Консольний інтерфейс (CLI): Інтерактивне меню для додавання (add), видалення (del), увімкнення/вимкнення (enable/disable) та перегляду списку правил (list) у реальному часі.
2.	REST API (мінімальний інтерфейс): HTTP-ендпорти (наприклад, за допомогою легкої бібліотеки на кшталт FastAPI або Flask у Python), що приймають JSON-запити для оновлення правил на льоту:
•	GET /rules — отримати поточний список правил.
•	POST /rules — додати нове правило.
•	PUT /rules/{id} — змінити параметри або статус існуючого правила.
•	DELETE /rules/{id} — видалити правило.
2. Механізм ведення журналу подій (Logging)
Система ведення журналу фіксує кожну подію відхилення пакета (або всі події згідно з налаштуваннями логування).
•	Параметри фіксації: Кожний запис у лог-файлі містить:
•	Точну мітку часу (Timestamp).
•	Причину блокування (наприклад, Blocked by rule #4: IP blacklist або Port restriction).
•	IP-адресу та порт джерела (Source IP:Port).
•	IP-адресу та порт призначення (Destination IP:Port).
•	Протокол та напрямок трафіку.
•	Зберігання даних: Журнал подій записується у локальний текстовий лог-файл (наприклад, firewall_events.log) у форматі CSV або JSON Lines для зручного парсингу, або зберігається у легкій реляційній базі даних (SQLite). Це забезпечує можливість швидкого пошуку, фільтрації та статистичного аналізу інцидентів безпеки за різними критеріями (за часовим інтервалом, IP-адресою джерела тощо).
3. Динамічне оновлення налаштувань та виявлення конфліктів
Динамічне оновлення без перезапуску
Основний потік перехоплення мережевого трафіку працює незалежно від модуля керування правилами. Таблиця правил зберігається у пам'яті у вигляді потокобезпечної структури (Thread-safe collection, наприклад, із використанням мютексів threading.Lock або блокувань). Під час надходження запиту на зміну правил через API чи консоль, потік керування оновлює пам'ять атомарно, що дозволяє застосовувати нові налаштування миттєво до наступного пакету без зупинки роботи служби.
Виявлення та вирішення конфліктів і дублікатів
Під час додавання або оновлення правила система автоматично запускає перевірку на наявність конфліктів:
1.	Дублювання: Якщо нове правило повністю збігається за критеріями (src_ip, dst_ip, protocol, src_port, dst_port) з існуючим, система відхиляє дублікат або оновлює його статус із попередженням оператора.
2.	Логічні конфлікти (Перекриття):
•	Конфлікт пріоритетів: Виявляються ситуації, коли загальне правило (наприклад, заборонити весь трафік з ANY) перекриває вузьке правило (дозволити конкретний порт).
•	Механізм вирішення: Система використовує алгоритм упорядкування за пріоритетом (priority) та специфічністю правила (правила з конкретнішими IP/портами мають вищий пріоритет незалежно від порядку їхнього введення, або ж застосовується принцип "перше знайдене правило застосовується"). У разі виявлення суперечностей виводиться попередження в консоль/лог із зазначенням ID конфліктуючих правил.
Висновки
У ході виконання лабораторної роботи було успішно спроєктовано та реалізовано прототип програмного брандмауера. Розроблено гнучку структуровану таблицю правил фільтрації за IP-адресами, портами та протоколами, інтегровано систему логування блокувань у файл/БД, а також реалізовано механізм динамічного оновлення налаштувань "на льоту" та перевірки правил на наявність дублікатів і конфліктів без зупинки основної служби брандмауера.
